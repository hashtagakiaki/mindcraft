# Native peer communication — stage 5 (2026-10-05)

`communication.sendToBot(recipient, message)` is exposed to generated SDK code only while `agent_runtime` is `codex-session`. It is tracked as an owned SDK call beneath the active ActionManager operation. The 2,000-character message is routed by the existing `ConversationManager` and MindServer `chat-message` route. The caller must have the current protected management credential; a native send never falls back to an anonymous or legacy route.

The hub derives the sender name and spawn from the authenticated socket, requires that socket to be the bot's currently registered connection, and checks its registered connection generation against the send envelope. The receiver generation is attached by the hub and checked against the receiving proxy. Registration ACKs echo the accepted connection generation. A replaced socket, stale spawn, unavailable recipient, or old hub generation cannot route a native inbox message. Legacy `{message, start, end}` conversation traffic continues through its existing path without task scope or delivery ACK.

The sender SDK promise settles only after the receiver accepts the message into an already-active native task's in-memory inbox. The ACK carries the sender task ID and a separate receiver task ID; it does not mean the receiver read the message, acted on it, or completed a goal. The message is supplied once as context to a following Codex turn. Native messages do not start or replace receiver tasks. Stop, task replacement, management replacement, and task completion invalidate queued inbox content; a cancelled sender operation rejects and ignores a late ACK.

Receiver message IDs are retained per authenticated sender spawn for the lifetime of the Agent process, with a named cap of 256 IDs; inbox depth is capped at 32. Operator task dispatch IDs are retained per Agent process with a cap of 256. Replaying the active accepted task ID returns acceptance without a second execution; after completion or cancellation it is rejected and cannot restart that task. When either retention cap is full, new IDs are rejected rather than evicting old replay protection. These in-memory records do not survive a process restart and make no crash-surviving exactly-once guarantee.

Offline evidence is in `tests/codex_session.test.cjs` and `tests/management_auth.test.cjs`. It covers generated SES SDK send ownership and ACK, cancellation with late ACK, once-only next-turn inbox delivery, duplicate IDs and full-cap rejection, receiver task/connection separation, inbox invalidation after task replacement, duplicate operator task IDs, current authenticated hub routing, old sender socket rejection, and the unchanged legacy chat shape. These fixtures prove protocol boundaries only; they do not establish two-bot gameplay benefit or collaboration quality.

The available case inputs do not include a trusted two-bot task template plus observer/readiness arrangement, so no multi-bot game artifact was created. The next useful experiment needs that input and an observer that can record each bot's task/result history, start/end inventory and elapsed time. It should ask whether explicit task ownership and direct peer messages leave any duplicate work, destructive overlap, or repeated operator instructions; compare outcomes from the same initial state, including task completion, elapsed time, re-instructions, and duplicated actions. Consider claims or assignment only if reduced loss exceeds communication delay and ongoing coordination cost. Claims, role assignment, shared progress ledgers, an orchestrating actor, cross-process persistence, and crash recovery remain deferred until those observations justify them.
